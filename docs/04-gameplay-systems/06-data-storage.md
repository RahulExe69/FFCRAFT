# Data Storage: persistence, rankings, and quotas

## What it is for

Garena's official Craftland Studio guide describes Data Storage as data stored outside the game process. Documented use cases include player archives, rankings, statistics, game settings, and sharing data between different games on the same map. The feature is optional; the guide warns that unloading the module invalidates related primitives, code, and configurations.

Official guide: [Data Storage](https://ffcraftland.garena.com/en/tutorial/fe/1-35).

## Three storage types in the guide

| Type | Keying model | Value constraints in the guide | Example uses |
|---|---|---|---|
| Normal/general data storage | Player UUID + script-defined key | Each table accepts one configured data type | Player archives/settings/progress |
| Ranking data storage | Custom key; table ranks by value | Integer values only; sorted ascending/descending; documented cap of 150 rows/table | Kill, score, points, or race leaderboard |
| Statistics storage | Predefined shared keys | Integer values only; documented maximum 120 tables | Total bosses defeated, total spend, global counters |

Do not mix the models. Normal storage is player-indexed, ranking storage is an ordered table, and statistics storage aggregates values under predeclared keys.

## Published-documentation limits (verify before release)

The official guide currently describes:

- 100 read operations per minute and 100 write operations per minute.
- Maximum key/value stored size of 4 KB (as phrased by the guide; confirm whether the current implementation constrains the combined record or value field).
- Up to 150 rows in each ranking-data table; additional values are not recorded after the cap.
- Up to 120 statistics-data tables.

These figures are preserved because they affect design, but the source page contains older contextual details and Craftland releases continue to change. Confirm the live Studio version's guide before relying on them in a published map.

## Important: distinguish the newer PC Data Store APIs

The current online API reference also lists a newer family of Data Store APIs, including `WriteToDataStoreV2`, `ReadFromDataStoreSteady`, and `ReadFromDataStoreByColumn`. The individual pages surfaced during this review label these as **Server Side** and **Only PC**. The older `WriteToDataStore` API page is explicitly marked **Obsolete**; avoid it in new code.

- [Write To Data Store V2](https://ffcraftland.garena.com/en/docs/api-31-1017) — writes a value with cross-map code read/write permission checking; takes sheet name, account UUID, key, value, map code, and a status output.
- [Steady Read From Data Store](https://ffcraftland.garena.com/en/docs/api-31-1006) — read a value without reading the cache; server-side, PC-only per the reference.
- [Read From Data Store By Column](https://ffcraftland.garena.com/en/docs/api-31-953) — read a table column by key and column index; server-side, PC-only per the reference.
- [Legacy Write To Data Store](https://ffcraftland.garena.com/en/docs/api-31-802) — marked Obsolete; do not use for new code.

Do **not** assume these PC-only code APIs are identical to the configurable Normal/Ranking/Statistics storage module described above, or that they are available in Craftland Mobile. These are separate documentation surfaces and may have different permission, key, caching, quota, and map-code rules. Confirm the correct system and exact current signature in the installed editor before implementation.

## Design for fewer operations

- Batch related fields when the configured value type allows it, instead of writing separate values to many tables. Garena's example stores position/orientation together and warns that multiple tables increase read/write usage.
- Avoid per-frame writes and unnecessary repeated reads.
- Cache non-authoritative presentation values during a match; persist at meaningful checkpoints or state transitions.
- Check each operation's success/result and handle missing records/default values.
- Validate value type and key/index carefully. The documentation warns that batch query results can be unexpected if the number/order of Account IDs and keys does not match.
- Keep data schema names stable. Changing the configured data type or unloading the module can invalidate code/configuration that expects the old structure.

## Storage table shapes

For the configured storage guide: normal data storage is table → player UUID → script key → value; ranking storage is table → custom key → integer value, with ranking order generated by value; statistics storage is table → predefined key → shared integer value.

A player archive can store a list/tuple/object-like supported value containing multiple related values if the configured storage accepts that type. Confirm current type support in the editor; patch notes for Studio 1.18.0 mention tuple values and Data Store read/write support, so do not assume old examples are the only possible schema.

## Published Data Center and local debugging

The official guide says persistent Data Storage is normally viewed in the Creator/Data Center for published maps, and documents a developer/local testing tool that exports data to a local JSON-like file (the page appears to misspell the extension as `.jason`). Treat that as a local testing mechanism, not a production API or a promise that local files are available to players.

## What not to store here by default

A match-only join counter, temporary cooldown, local animation state, or short-lived trigger flag usually belongs in runtime state rather than persistent storage. Data Storage is more appropriate when state must survive the game process or serve cross-match rankings/statistics. This is a design recommendation based on the storage model, not a platform-enforced rule.

## Security and correctness cautions

- Do not trust a client-only score or client-provided storage write for competitive outcomes; validate gameplay results with appropriate server-side logic.
- Do not use display names as stable keys unless the platform guarantees they are unique and stable.
- Define what happens when reads fail, records are absent, or storage quota is exhausted.
- Avoid storing large lists when a small normalized schema is enough; every read/write counts toward usage constraints.
- Add a version/migration plan before changing a published schema.

## Testing checklist

- [ ] Module is loaded and the table/type/key configuration matches the code.
- [ ] First-time player and returning player behave correctly.
- [ ] Read/write success and failure paths are handled.
- [ ] Repeated matches do not exceed operation limits.
- [ ] Ranking sort order and row cap are correct.
- [ ] Missing records and invalid values have safe defaults.
- [ ] Local test data matches expectations and the published Data Center view agrees after publication.
- [ ] Limits were re-checked against the current release documentation.
- [ ] API platform labels, status codes, caching behavior, and map-code scope were verified for the selected storage system.
